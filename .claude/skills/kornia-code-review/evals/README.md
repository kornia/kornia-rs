# kornia-code-review evals

Cases the review skill must keep getting right, run with `claude plugin eval`.
Three kinds:

- **Planted defects** (`gray-copy-scope`, `checker-misses-stale-fact`,
  `compose-plane-fit`, `dup-homography-inverse`, `novel-otsu`): a PR with
  known defects. Measures recall.
- **Mined from history** (`mined-*`): the revert of a real kornia-rs fix on
  the current tree, so the PR reintroduces a bug that shipped. Found with
  `scripts/skill_evals.py mine` (SZZ: fix commit, then `git blame` to the
  commit that introduced it), then vetted by hand.
- **Negative controls** (`clean-*`): a merged, clean PR. The review must not
  raise blocking or major findings. Measures false positives; without them a
  skill that flags everything scores full recall.

## Case files

- `patch.diff`: applied to the copied tree. `check_skills.py` runs
  `git apply --check`, so a case goes stale loudly when the code moves.
  Whitespace hooks skip `evals/**.diff` and the generated `precision.md`
  graders (they embed the diff); never let a formatter touch them.
- `merged.diff` (controls only): the PR's change, already in the tree
  (`check_skills.py` checks it still reverse-applies). The reviewer gets it and
  `patch.diff` as one `pr.diff`.
- `pr.md`: the PR title and body the reviewer sees, as `PR.md`.
- `issue.md` (optional): what `gh issue view` prints for the linked issue,
  given to the reviewer as `ISSUE.md`. `checker-misses-stale-fact` has none on
  purpose, to keep the unreadable-issue rule tested.
- `expected.md`: the human key. Never shown to the reviewer, and no backtick
  term in it may appear in `SKILL.md` (`check_skills.py`; a key the skill
  spells out turns the case into a recall test of the skill text).
- `prompt.md`, `case.yaml`, `scaffold.sh` (one-line wrapper of
  `../scaffold.sh`): what `claude plugin eval` runs.
- `graders/*.md`: one `llm` grader per required key item with concrete PASS
  and FAIL conditions; `verdict.md` (regex) on defect cases; `skill-fired.md`
  (WITH-arm indicator, not scored); `precision.md`, generated by
  `python3 scripts/skill_evals.py sync` from the key, PR, issue and diff, flags
  a false blocking or major finding. It is a WITH-arm indicator, not scored,
  until a judge is calibrated on it: a Sonnet judge gave the same review 0/3
  and 3/3 on 2026-10-24. Controls are scored by `no-blocking.md`.
  `check_skills.py` fails while a `precision.md` is stale.

## Run

`pixi run skills-eval` runs every case (Claude Code >= 2.1.269 and its
sandbox: `bubblewrap` and `socat` on Linux). Each run:

- `scaffold.sh` copies the repo into an empty workspace (no target, .git or
  .pixi), applies the case, writes `PR.md`, `pr.diff` and `ISSUE.md`, and
  deletes the case directories, so the reviewer never sees a key or grader;
- the reviewer gets `prompt.md`, Bash inside the sandbox (no network) and, in
  the WITH arm only, this skill. The W/OUT arm is the same run without it (the
  skill files are still in the copied tree; the agent is just not given them);
- the judge scores the final review with `graders/`.

Flags: `--case <name>`, `--runs N`, `--model`, `--judge-model` (always a
different model from the reviewer: judges favour their own model's text),
`--ablation none` (WITH arm only), `--json <file>`, `--max-cost-usd`. Results
go to `evals/results/` (ignored). CI: the `Skills Eval` workflow, on demand or
with the `run-skill-evals` label.

A skill edit is done when every case passes WITH the skill on Opus, and Sonnet
and Haiku do not drop by more than their run-to-run spread. One run per arm is
noisy: on 2026-10-24 two full runs of the same skill gave Sonnet 7/8 and 5/8
(WITH), so compare pass rates over `--runs 3` or more, not single runs:

```bash
for m in haiku sonnet opus; do
  j=$([ $m = opus ] && echo sonnet || echo opus)
  pixi run skills-eval --model $m --judge-model $j --runs 3 --json results-$m.json
done
python3 scripts/skill_evals.py report results-*.json
```

`report` prints, per case and arm, passes over runs, a Wilson 95% interval,
pass^k (the chance that k runs all pass: a defect caught 2 of 5 times is not
caught reliably) and the WITH-minus-W/OUT score delta. With 8 cases only a
large delta means anything; read the intervals.

## Check the judge

Read reviews, not only scores. `report --dump DIR` writes every review and a
`labels.json` with the judge's verdicts; fill in each `"human"` (the
reference verdict) and `"labeller"` (a person, or a second grader that never
saw the judge's verdicts), and run
`python3 scripts/skill_evals.py calibrate DIR/labels.json`. It prints agreement
and Cohen's kappa and fails below 90% agreement; fix the graders, not the
labels. `calibrate --rejudge <model>` re-asks the judge with the current
graders, so a grader edit can be checked against the stored reference labels
without new reviews. `calibration/` holds the committed labelled set: 46
verdicts on 11 Sonnet reviews, labelled by a second Opus grader that never
saw the judge's verdicts. `calibrate calibration/labels.json` reproduces the
stored judge (old graders): 91% agreement, kappa 0.78; `--rejudge opus`
with the tightened graders gave 96%, kappa 0.90 on 2026-10-24. The labeller is
the same model family as that judge, which can inflate agreement; human
labels (set `"labeller"`) are the stronger check.

## Held-out cases

`skill_evals.py mine --make <fix-sha> <name>` writes an unvetted case to
`evals/heldout/<name>/`, which is ignored by git and by `check_skills.py`
and is picked up by `claude plugin eval`. Keep a few there: they are never
committed, so their keys never reach whoever edits the skill. Vet a case
before trusting its score, and rotate in newly mined ones as fixes land.

## Add a case

When a review missed a defect that surfaced later, reduce it to the smallest
diff that reproduces it (or mine it) and commit it with the skill change that
catches it: `patch.diff`, `pr.md`, `expected.md`, optional `issue.md`, then
copy `prompt.md`, `case.yaml` and `scaffold.sh` from another case, write one
`graders/<item>.md` per required item, and run `skill_evals.py sync`.
